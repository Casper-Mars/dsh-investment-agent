# Skill 创作合规规范（skill-authorship）

## 定位

`skill-authorship` 是**编写合规 skill 的唯一规范**。当你要**创建或修改 `data/skills/` 下的任何 `SKILL.md`** 时，必须先遵循本规范，产出符合「结构契约 + 红线」的可进化资产；否则「进化」产物会成为不合规资产。

本 skill 是**固件**（不是可进化方法论）：它随插件包静态内置，**不落 `data/skills/`**、不参与 git 进化链 / 热更新 / 复盘改写，仅在你要写改可进化 skill 前被注入，作为写改的约束。

> **与 `strategy-authorship`（可进化）区分**：两者命名相近、性质不同——
> - `strategy-authorship`（可进化）教你怎么写**某标的的策略文档**；
> - `skill-authorship`（固件）教你怎么写**skill 本身**。
> 前者是方法论、会被复盘进化；后者是规范、固定不变。不要混淆作用对象。

## 结构契约

一份合规的 `SKILL.md` 必须满足：

1. **frontmatter 三字段齐全**（缺一不可）：
   - `name`：skill 名，kebab-case，必须与所在**目录名一致**。
   - `description`：面向模型的路由描述，说清「这个 skill 提供什么能力」。
   - `whenToUse`：触发条件（写法见下节）。
2. **正文骨架**：至少包含「触发条件 / 步骤 / 边界」三块，让模型知道**何时用、按什么步骤做、不越界**。

## whenToUse 写法规范

`whenToUse` 不是泛泛的「需要时」，必须**可判定、可枚举**：

- 写明**具体触发场景**（如「即将创建或修改 `data/skills/` 下的任何 `SKILL.md` 时」），而非「需要写 skill 时」。
- 用**可判定的动作 / 对象**描述，让模型能据输入自行判断是否命中。
- **不写具体数值或标的**：不出现「某价位」「某百分比」「某具体股票 / 代码」。
- **不枚举具体资产 / skill 名**：不出现「统筹 A/B/C 三个 skill」这类把同类对象逐个列出的写法。`whenToUse` 是**路由描述**，只写「什么场景下用我」这一层；「调哪个 skill / 去哪个资产」属**正文**，不属 `whenToUse`。
  - 为什么：一旦在 `whenToUse` 里列出具体对象，资产每增删一个就要回来改一次——**漂移会被反复制造**；抽象、稳定的路由描述才不必随资产扩张维护。

## 硬性红线

新建或改写 skill 时，以下行为**一律禁止**：

- ❌ `name` 与目录名不一致（skill-filesystem 按目录发现，`name` 必须以目录名为准）。
- ❌ 缺 `name` / `description` / `whenToUse` 任一字段。
- ❌ 正文写成散文（无结构、无步骤、无边界）。
- ❌ 塞入固件内容（把「如何注册 / 装配」等固件实现细节写进可进化 skill）。
- ❌ 混入策略参数（把某标的的价格、阈值、网格间距写进 skill；这些属于「该标的策略文档」）。
- ❌ 写死具体数值 / 标的（skill 必须标的无关，具体数值由 agent 按标的落入该标的的策略文档）。
- ❌ `whenToUse` 里枚举具体 skill 名 / 资产名 / 文件名（把「路由描述」降格成「引用清单」，资产一变动即漂移）。

## 自检清单

写完逐条打勾，有一条不满足即回到正文修正：

- [ ] `name` 为 kebab-case，且与目录名一致。
- [ ] frontmatter 三字段 `name` / `description` / `whenToUse` 齐全。
- [ ] `whenToUse` 可判定、可枚举，不含具体数值 / 标的 / **skill 名 / 资产名**。
- [ ] 正文含「触发条件 / 步骤 / 边界」骨架。
- [ ] 无固件内容、无策略参数、无写死数值。
- [ ] 全文标的无关，未写成散文。
