# 资产进化

## 一句话

发现问题就改资产。改完跑自检，不过就继续改，过了就提交。循环直到通过。

## 资产范围

**资产＝`assets` 目录下的一切**（`skills`、`strategies`、`programs`、`tasks`）。判断只看位置：在 `assets` 下，且不在固件清单里，就是资产。

**固件（不可改，虽在 `assets` 下）**：本 skill、`skill-authorship`、任务程序创作规范。

**`assets` 之外（不可改）**：系统提示、原则、红线、铁律。

## 什么时候改

任一环节（分析、决策、盯盘、复盘、执行）觉察到以下之一就动手，否则只记录：

1. 指标异常；
2. 同一失败出现第二次；
3. 能力缺陷可复现（采不到、算错、没执行）；
4. **某个做法明显有效**——做对了也要沉淀成条款或程序。

「感觉可以更好」不算。

## 改哪个

先定位缺口，再落到资产。

| 现象 | 改什么 |
|---|---|
| 该采的没采到、读数失真 | 任务程序 / 工具 |
| 方向、区间、信号判错 | 方法论 skill / 策略文档 |
| 该触发没触发、动作算错 | 任务程序 / 工具 |
| 策略条款冲突、缺失 | 策略文档 |
| 同一类坑跨标的重现 | 方法论 skill |

## 怎么改

1. **改**。
2. **跑自检**（见下）。有不过的项，带着不过的项继续改，回到第 1 步。
3. **全过后提交**：这次提交就是「追加一条修改记录」。
4. **下次看一眼**：该资产下次产生结果时（下一次复盘 / 下一次同类判断 / 下一次执行 / 下一次调用），看结果是否有问题。有问题就撤：`git revert`，或按 diff 反向修改后重新提交——**撤销本身也是一条修改记录**。

最多 5 轮。5 轮还不过，停手，把卡在哪交给人。

## 修改记录＝git

- **载体**：git 提交历史，不另建记录文件。审计入口是 `git log`。没提交＝没发生。
- **两个仓**：`assets/skills` 是独立仓；`assets` 是外层仓（strategies / programs / tasks）。提交必须落在被改资产所属的仓。
- **append-only**：只追加。禁止 amend、rebase、force-push。
- **提交身份**：固定 `dsh-ia <dsh-ia@localhost>`，`core.autocrlf=false`，不依赖宿主机 git 配置。
- **只记操作，不判结果**：写清改了什么、为什么改（场景 + 教训/经验），不写「效果良好」这类结论。

## 自检

- [ ] 属于四类触发之一，说得出具体事实
- [ ] 定位到 `assets` 下的具体资产
- [ ] 改动涉及的引用已同步
- [ ] 没有改固件
- [ ] 提交信息含：改了什么、为什么改
- [ ] 说清了下次在什么事件上会再看到它
- [ ] 轮次未超 5

## 抽象层与具体实现的差别

系统提示要求「定度量标准、在观测窗口内验证」——这是**宏观能力进化**的表述，讲的是能力会正确进化。

具体实现做不到当场判断方向对不对：改完只能等真实场景考验。所以：

- 本 skill 只保证这次进化**行为完整、可追溯、可撤销**；
- **不保证进化方向正确**，方向错了由后续进化纠正；
- 因此不设度量标准、不设观测窗口，验证点＝该资产下一次自然产生结果的事件。
